# Codex 구현 지시서 — Youth Kitty Planner (청년냥이 플래너, YKP)

당신은 SSAFY AI 코어 프로젝트 3회차의 **구현 담당 시니어 엔지니어**다. 이 프롬프트와 같은 레포의 `docs/ARCHITECTURE_AND_SCHEMA_v1.md`는 구현 계약이며, `docs/PROJECT_STRUCTURE_YKP.md`는 신규 프로젝트의 목표 폴더 구조 및 기존 레포 적용 가이드다. 프로젝트의 최상위 외부 요구사항은 사용자 제공 `AI코어프로젝트_3회차_요구사항정의서(4).pdf`다. PDF가 실제 레포에 없으면 문서가 없다는 사실을 보고하고, 제공된 스키마 문서의 F/NF 매핑을 기반으로 진행하되 PDF 검증은 BLOCKED로 표기해. 사용자에게 받은 첨부 PDF를 찾을 수 있다면 직접 읽고 판단해. **요구사항을 추측해서 PASS로 표시하지 마.**

## 작업 방식: 단계별 구현 + 보고서 + 검토 게이트

- 먼저 레포 전체를 조사해 이미 구현된 기능, 환경변수, 의존성, 엔트리포인트, Git 상태를 파악해. 실제 존재하지 않는 파일/기능을 가정하지 마.
- `master/main` 브랜치 내용을 강제로 덮어쓰거나 강제 push 하지 마. 기존 프로젝트를 손상시키지 말고 필요한 최소 변경만 수행해.
- **이번 지시에서 실제로 진행할 범위는 Phase 0과 Phase 1이다.** 완료 또는 차단 시 `reports/phase-01.md`를 작성한 후 **멈춰**. 다음 Phase는 사용자가 보고서를 외부 검토받고 승인할 때만 진행해.
- 이후 모든 Phase에서도 같은 원칙을 지켜: 구현 → 실제 테스트 → 파일·로그·증거가 포함된 보고서 → 중지 → 승인 후 다음 단계.
- 진짜 실행하지 않은 테스트, 확보하지 못한 응답, 성공하지 못한 호출은 절대로 '성공'으로 작성하지 마.
- 원본 API 키, Bearer token, 고객의 민감정보를 코드·로그·보고서·커밋·화면에 넣지 마. 키는 `.env`(gitignored)로만 로드하고, `.env.example`에는 변수 이름만 사용해. 이미 노출되어 있으면 비밀정보를 보고서에 출력하지 말고 교체 필요성만 알리기.
- 구현을 위해 기술 변경이 꼭 필요하면 **원안/변경안/근거/요구사항 영향**을 보고서에 명확히 적어. SSAFY 필수 기능 축소·삭제 금지.

## 적용 범위

- 표시용 공식 브랜드: **Youth Kitty Planner (청년냥이 플래너, YKP)**, 슬로건 **Your Smart Guide to Life in Korea**. README/UI/보고서에 적용. 기존 코드 식별자, API 경로, DB 이름은 단순 브랜딩만으로 변경 금지.

- MVP: 첫 취업 후 독립 준비 플래너. 과거 임대차 거래 후보를 조회하여 현실 예산 검증, 건물 수준 상세 확인, 카카오 로컬 위치 보조 데이터 조회, 실행 계획 생성·관리.
- 핵심 기술: Python 3.10+, FastAPI, Pydantic v2, LangGraph, SQLite, 독립 프론트(Vue 3 권장; 기존 레포 구조 우선).
- 필수: F3001~F3019 전부, NF3001~NF3007 전부. 심화 F3020/F3021/F3022/F3023는 MVP 완료 전 착수하지 말 것.
- 세 API 키는 사용자가 발급받았으나 **실제 호출 결과 미확인**. 환경변수명은 `KAKAO_REST_API_KEY`, `MOLIT_RENT_API_KEY`, `BUILDING_HUB_API_KEY`를 기본으로 하되 기존 설정이 있으면 별도 설정 매핑을 통해 호환하도록 해. 공공데이터 키의 decoding/encoding 처리는 HTTP 라이브러리의 URL 인코딩과 중복되지 않도록 확인.

## Phase 0 — 레포 점검 (구현 전)

1. `docs/PROJECT_STRUCTURE_YKP.md`를 읽고, 실제 폴더/파일 구조, 현재 브랜치, 기존 코드, 실행 가능 상태, 의존성 목록 파악. 신규 레포라면 목표 구조를 따르되, 기존 코드가 있으면 최소 변경 원칙을 적용.
2. PDF 요구사항 F3001~F3019/NF3001~NF3007과 기존 구현을 비교해 누락 항목 작성.
3. `docs/PROJECT_STRUCTURE_YKP.md`의 모듈 경계를 확인하고 실제 레포와 차이표를 작성. API 클라이언트·Agent·모델·서비스·DB·화면·테스트의 책임을 구분. 사용자가 작성한 코드를 불필요하게 재구성하지 마.
4. 인증키/토큰/DB 파일 및 cache 파일의 gitignore 상태를 점검. 키 값 자체는 절대 출력하지 마.
5. Phase 1에서 검증할 지역·월 데이터를 테스트 파라미터로 준비하고 문서화(개인 위치 기반 가정 불필요).

## Phase 1 — 외부 API 3종 실제 호출·Tool 명세/테스트

반드시 3개의 **서로 다른 정보 API**를 각각 실제로 호출해라.

A. 카카오 로컬 API: 주소 검색과 필요 시 장소 검색. 인증·코드·좌표·법정동 데이터·빈 결과 확인.
B. 국토부 연립다세대 전월세 실거래 API: 법정 시군구 코드 및 계약월로 과거 거래 후보 조회. 금액 원문 단위와 정수 원화 변환, 계약 날짜, 건물·지번 관련 실제 응답 필드를 검증.
C. 국토부 건축HUB 건축물대장 표제부 API: 조회 인자, 건물 속성, 페이지네이션, 응답 메타데이터 확인. 실거래 후보와 같은 **건물 수준**인지 대조 가능한 근거를 실험.

각 API에 대해 반드시 남겨야 할 산출물:
- 공식 문서 URL, 제공기관, 인증 유형, 현재 확인된 호출 한도·약관, 조회 URL/파라미터(키는 마스킹).
- HTTP 상태와 provider 내부 resultCode/오류 처리, 실제 필드명/형식/단위, 성공/실패/빈 응답 사례.
- 키/개인정보/주소 상세를 제거한 **실제 응답 구조 샘플** (`reports/evidence/phase-01-*.json` 또는 Markdown).
- `ToolSuccess|ToolFailure` 응답 구조에 맞는 Pydantic 스키마, Tool 등록 내역, `ok/error/meta` 정규화.
- `search_location`, `search_rental_transactions`, `get_building_detail`의 실제 호출과 mock 기반 실패·schema mismatch 테스트.
- 후보→상세 연결 가능 여부: `MATCHED_BUILDING/AMBIGUOUS/NOT_FOUND/UNKNOWN`으로 보고하며, 시군구 코드만 같다고 매칭 성공 처리 금지.
- 과거 거래 정보를 현재 매물 또는 계약 가능/안전으로 표시 금지.
- 호출 실패 시 MOCK 테스트는 실행해도 **실 API 연동은 BLOCKED**. 인증 문제·승인 상태·쿼터/응답 차이를 설명하고 재시도/대체 API 방안 제시.

**1일 차 16시 API 3종 호출 검증 게이트**가 PDF에 있어. 기한 내 실패하면 PDF에 명시된 제공 영화 도메인 팩 전환 여부를 즉시 사용자에게 알려야 한다. 임의로 API 충족으로 표기하지 말 것.

## 후속 Phase (이번 지시에서는 수행하지 않음)

- Phase 2: `AgentState`, 조건 추출, LangGraph `분석 → 계획 → Tool 실행 → 결과 통합 → 제약 판단 → 필요 시 재계획 → 응답`, Memory 조건 patch, 실행 횟수 최대 3회, Tool 결과 재사용, 규칙 기반 PASS/FAIL/UNKNOWN, LLM 사용 이유 이벤트. F3005~F3011.
- Phase 3: SQLite 계획/Task 구조, 날짜·시각·금액, 계획 CRUD, 중복 일정 저장 허용+경고, 독립 이벤트 Publisher·Logging Agent, 원본 이벤트 LLM 없이 저장·조회·삭제, FastAPI chat/plans/logs. F3012~F3017.
- Phase 4: 프론트 분리, 대화·계획 관리 화면, Agent 단계·Tool·재계획·진행·오류 상태 시각화, 대표 시나리오 5개 이상과 NF 검증, README, 제출 증거. F3018~F3019 및 NF 전체.
- **모든 Phase에서 구현하지 않은 것을 완료로 보고하지 마.**

## 강제 설계 규칙

1. DB, Pydantic, Tool, Agent, API, 로그 스키마는 `docs/ARCHITECTURE_AND_SCHEMA_v1.md` 기준. 변경 시 이유와 DTO 호환성 기록.
2. `AgentState`는 대화 실행 상태이고 `plans/plan_tasks`는 장기 저장 데이터. Checkpointer만으로 계획 저장 완료 처리 금지.
3. 모든 Tool은 정형 성공/실패 반환. API 원문 자체를 LLM Tool 결과로 무제한 전달하지 마. 원문 내부 오류를 사용자에게 노출하지 마.
4. `replan_count`는 사용자 요청(run)마다 0에서 시작해 최대 3. 같은 데이터를 다시 조회하지 않도록 요청 내 캐시. 고정 제약 자동 완화 금지.
5. 날짜만 정해진 Task에 시각을 지어내지 마. 충돌 검사 시 시간이 정해진 작업 간에만 검사, 충돌해도 저장하고 warning 반환.
6. 외부 원문은 신뢰하지 않는 데이터이며 임의 Tool 실행 지시로 처리하지 마. Tool whitelist+Pydantic 입력 검증 필수.
7. 로그는 발행 전 민감정보를 제거한 구조화된 **원본 이벤트**를 보존. 구독·저장에 LLM 호출 금지. 구독자 장애와 메인 실행을 격리. 로그 수정 API 금지.
8. 세션/계획/로그 소유권을 서버에서 검증하고 사용자가 임의 thread_id·session_id로 타인 데이터를 조회할 수 없게 해.
9. JSON DTO 검증·날짜/시간대·화폐 정수 단위와 오류 코드를 테스트해.
10. PDF에 요구되는 증거(실행 로그/그래프/호출 결과/화면/README)를 최종 단계까지 관리해.

## 보고서 의무 (매 Phase 종료)

`docs/PHASE_REPORT_TEMPLATE.md`의 항목과 폴더 구조 점검표를 빠짐없이 채워 `reports/phase-XX.md` 작성. 포함사항:

- Phase 목적과 실제 범위 / 변경 파일 및 핵심 구현 내용
- F3001~F3019 + NF3001~NF3007 상태 (`PASS/FAIL/BLOCKED/NOT_STARTED`)와 **증거 파일·테스트 명령·결과**
- 외부 호출은 **실 API / 목킹**을 분리하고 성공 수·실패 수·실패 이유 기재
- 테스트 실제 실행 명령과 종료 코드/요약, 중단된 이유
- 보안 점검(키 미노출, `.env` 추적 제외, 인증/소유권)
- 스키마 이탈, 미해결 위험, 다음 Phase를 시작하기 전 결론
- 마지막 줄에 `REVIEW REQUIRED — 다음 단계 미착수` 명시

### 완료 조건

이번 응답은 Phase 0~1의 실제 수정 결과와 보고서 경로를 제공하고 멈춰라. 사용자와 검토자가 보고서를 보고 승인하면 다음 Phase를 지시할 예정이다. 실 API 키가 없거나 네트워크 제한이면 실행 불가 사유를 명시하고 mock 검증만 보고한 뒤 중단해라. 성공한 척 하지 마.
